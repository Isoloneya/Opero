**Версія:** 0.1.0

**Технологічний стек:** Next.js, TypeScript, Python, FastAPI, SQLAlchemy, Alembic, SQLite, Neon PostgreSQL, Tailwind CSS

## AC-01. Опис та постановка задачі

### Назва проєкту

Opero

### Предметна область

Opero — веб-застосунок для внутрішніх операцій невеликої компанії. Система об’єднує складський облік, заявки на матеріали, погодження заявок, задачі та журнал дій.

### Проблема

Працівники часто ведуть залишки в Excel, надсилають заявки через месенджери й погоджують їх усно. У такому процесі складно встановити актуальний залишок товару, статус заявки, відповідального працівника та історію рішень. Opero створює єдиний робочий простір для цих процесів.

### Цільова аудиторія

- невеликі сервісні та будівельні компанії;
- торгові компанії з одним або кількома складами;
- виробничі команди з внутрішнім рухом матеріалів;
- менеджери, комірники, виконавці та керівники.

### Призначення системи

Система дозволяє вести довідник товарів і складів, контролювати залишки, створювати заявки на видачу або закупівлю товарів, проходити погодження та керувати внутрішніми задачами.

### Основні сценарії використання

1. Адміністратор створює користувачів, склади та товари.
2. Комірник фіксує надходження товару на склад.
3. Працівник створює заявку на видачу товарів зі складу або закупівлю товарів.
4. Менеджер погоджує або відхиляє заявку.
5. Комірник видає погоджені позиції та система оновлює залишки.
6. Менеджер створює задачу, призначає виконавця та встановлює дедлайн.
7. Виконавець змінює статус задачі, а керівник контролює прогрес на дашборді.
8. Уповноважений користувач переглядає журнал дій за обраний період.

### Межі версії 0.1.0

До версії входять складський облік, заявки, погодження, задачі, ролі користувачів, дашборд, пошук, фільтрація, пагінація та аудит дій. Інтеграції з обліковими системами, сканування штрихкодів, фінансовий облік, email-сповіщення та багаторівневі маршрути погодження не входять до обсягу версії.

## AC-02. Архітектура та структура системи

### Загальний підхід

Проєкт є монорепозиторієм із незалежними клієнтською та серверною частинами. Взаємодія відбувається через REST API у форматі JSON.

### Компоненти системи

| Компонент | Технологія | Відповідальність |
|---|---|---|
| Frontend | Next.js, TypeScript, Tailwind CSS | сторінки, форми, навігація, клієнтська валідація, виклики API |
| Backend | FastAPI, Pydantic | HTTP API, валідація, авторизація, бізнес-правила |
| Дані | SQLAlchemy, Alembic | моделі, репозиторії, міграції |
| База даних | SQLite локально, Neon PostgreSQL у Vercel | постійне зберігання даних |

### Backend-архітектура

| Шар | Відповідальність | Заборонено |
|---|---|---|
| Router | HTTP-запит, Pydantic-валідація, виклик сервісу, HTTP-відповідь | бізнес-логіка та прямі ORM-запити |
| Service | правила домену, перевірка прав, транзакційні операції | формування HTTP-відповідей і прямі запити до моделей |
| Repository | читання та зміна даних через SQLAlchemy | бізнес-правила та перевірка ролей |

## AC-04. Модель даних

| Сутність | Основні поля | Призначення |
|---|---|---|
| User | id, full_name, email, password_hash, role, is_active, created_at | обліковий запис працівника |
| Warehouse | id, name, location, is_active, created_at | склад або місце зберігання |
| Product | id, sku, name, unit, minimum_stock, is_active, created_at | товар або матеріал |
| InventoryBalance | id, warehouse_id, product_id, quantity, updated_at | поточний залишок товару на складі |
| StockMovement | id, warehouse_id, product_id, type, quantity, reference_type, reference_id, created_by, created_at | історія надходжень і видач |
| Request | id, number, type, status, warehouse_id, author_id, approver_id, rejection_reason, created_at, approved_at | заявка на видачу або закупівлю |
| RequestItem | id, request_id, product_id, requested_quantity, issued_quantity | позиція заявки |
| Task | id, title, description, status, priority, assignee_id, created_by, due_date, completed_at, created_at | внутрішня задача |
| AuditLog | id, actor_id, entity_type, entity_id, action, payload, created_at | незмінна історія дій |

### Правила цілісності даних

- SKU товару та email користувача мають бути унікальними.
- Комбінація складу і товару має один запис поточного залишку.
- Кількість товару завжди більша за нуль у рядку руху або заявки.
- Видача не може перевищувати погоджену кількість і доступний залишок.
- Відхилена або видана заявка не може бути повторно погоджена.
- Задача зі статусом завершено повинна мати дату завершення.
- Записи журналу дій не редагуються і не видаляються через API.

## AC-05. Функціональні вимоги

### Автентифікація та користувачі

- Система дозволяє увійти за email і паролем.
- API видає JWT access token після успішного входу.
- Користувач без токена не має доступу до захищених маршрутів.
- Адміністратор може створити користувача, змінити його роль і деактивувати обліковий запис.
- Деактивований користувач не може увійти до системи.

### Склади, товари та залишки

- Адміністратор створює, редагує та деактивує склад.
- Адміністратор створює, редагує та деактивує товар.
- Комірник реєструє надходження товару із зазначенням складу, товару та кількості.
- Система створює рух товару й оновлює поточний залишок атомарно.
- Система показує позиції, де залишок менший або дорівнює мінімальному запасу.
- Деактивований товар не можна додати до нової заявки чи надходження.

### Заявки та погодження

- Користувач створює заявку типу видача або закупівля з однією чи кількома позиціями.
- Нова заявка отримує унікальний номер і статус очікує погодження.
- Автор може редагувати або скасувати лише заявку зі статусом очікує погодження.
- Менеджер або адміністратор може погодити заявку.
- Менеджер або адміністратор може відхилити заявку лише з причиною відхилення.
- Комірник бачить лише погоджені заявки типу видача.
- Комірник фіксує видану кількість по кожній позиції.
- Після повної видачі заявка отримує статус видано.
- Видача створює рух товару та зменшує залишок у межах однієї транзакції бази даних.

### Задачі

- Менеджер і адміністратор створюють задачі та призначають виконавця.
- Задача має назву, опис, пріоритет, дедлайн і статус.
- Доступні статуси: нова, у роботі, на перевірці, завершено, скасовано.
- Виконавець може змінювати статус тільки власної задачі.
- Менеджер і адміністратор можуть редагувати, скасовувати та завершувати будь-яку задачу.
- Простроченою є незавершена задача з дедлайном раніше поточної дати.

### Дашборд та аудит

- Дашборд показує кількість активних заявок за статусом.
- Дашборд показує кількість прострочених задач і задач поточного користувача.
- Дашборд показує товари з низьким залишком.
- Журнал дій містить автора, дію, сутність, ідентифікатор та дату.
- Доступний пошук і фільтрація журналу за користувачем, типом сутності, дією та періодом.

|---|---|---|

## AC-08. Валідація та обробка помилок

| Поле або дія | Правило | Рівень |
|---|---|---|
| Email | обов’язковий, коректний формат, унікальний | Pydantic, service |
| Пароль | від 8 символів | Pydantic |
| Назва товару або складу | від 1 до 120 символів | Pydantic |
| SKU | від 1 до 64 символів, унікальний | Pydantic, service |
| Одиниця виміру | від 1 до 20 символів | Pydantic |
| Кількість | число більше нуля, до трьох знаків після коми | Pydantic |
| Дедлайн задачі | не раніше дати створення | service |
| Відхилення заявки | причина обов’язкова, до 500 символів | Pydantic |
| Видача товару | не перевищує залишок і погоджену кількість | service |

Очікувані помилки бізнес-логіки перетворюються глобальним обробником на єдиний формат API. Непередбачена серверна помилка не розкриває технічних деталей клієнту.

## AC-09. Безпека

- Паролі зберігаються тільки як bcrypt-хеші.
- JWT підписується секретом із змінних середовища та має обмежений строк дії.
- Перевірка ролі виконується на сервері перед кожною захищеною дією.
- SQLAlchemy використовує параметризовані запити.
- Секрети не зберігаються в репозиторії.
- Дані користувача в інтерфейсі відображаються без небезпечного HTML.
- CORS дозволяє лише адресу frontend-застосунку у production-середовищі.
- Усі зміни критичних сутностей фіксуються в журналі дій.

Локальна розробка використовує SQLite через `sqlite:///./opero.db`. Vercel використовує рядок підключення Neon через змінну `DATABASE_URL`.

## AC-12. Розгортання

- Frontend і FastAPI розгортаються на Vercel в одному репозиторії.
- FastAPI працює як Vercel Function за маршрутом `/api`.
- Neon PostgreSQL використовується для preview і production-середовищ.
- SQLite використовується тільки локально та в ізольованих тестах.
- Міграції Alembic застосовуються до Neon окремою контрольованою командою перед першим використанням нової схеми.
- Змінні середовища налаштовуються у Vercel і не потрапляють до Git.
